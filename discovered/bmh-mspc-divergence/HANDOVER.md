## 2026-10-03 — connection: match the permutation on the confound, and test the other classes (orchestrator note, additive; nothing below altered)

Posted by the orchestrator, carrying a result from the 2026-10-02 Linear A validation panel into the
folders whose arguments have the same shape. Nothing below this section is changed or contested.

**(a) A label permutation must be matched on whatever the label is confounded with.** Linear A's
Scribe-9 cohesion result (p < 0.01) turned out to be an artefact of an unmatched null: the scribe
label is confounded with **tablet size**, Scribe 9 being that archive's largest hand, so a free
permutation of labels compared long documents against short ones rather than one scribe against
another. Permuted **within strata of the confound**, on the claim's own statistic, it moved to
**p = 0.12 to 0.57**. Any grouping variable can carry such a confound — hand, scribe, author,
compiler, witness, findspot, archive, period, genre, length, transmission branch.

**(b) Run the identical test on the classes you did not hypothesise, before calling the effect yours.**
The same validator ran it across the other eleven Haghia Triada scribes and found the effect **present
for Scribe 6 too** — making it a corpus-general scribal-department property, already established
elsewhere with proper nulls, rather than a finding about Scribe 9. It was the *absence* of that
comparison, not the p-value, that sank the criterion. This is the cheaper half and the one more often
skipped: it needs no new data, because you already hold the other classes.

**Operationally:** name the nuisance variable before computing anything; permute within its strata and
say which strata in the write-up; re-run the identical pipeline on every other class and report the
statistic's full distribution across classes, not only your class's value; and if the effect shows up
in classes you did not predict, the honest claim is about the corpus, not about your class.

This is **not** the same rule as *calibrate a shuffle null at the target's own token count* (carried
2026-10-02). That one is about comparing documents of different lengths; this one bites even when every
unit is the same length. Same diagnosis, different fix: there you block to a common length, here you
permute within strata and then repeat the whole test on the classes you were not interested in.

Full entry: `board/log/2026-10-03-connection-match-the-null-on-the-confound-and-test-the-other-classes.md`.
Source measurement: `board/log/2026-10-02-validation-linear-a-v2.md`. Short form in `board/PRACTICES.md`.

**Why this folder.** Its divergence argument compares two collections of witness statements, and the
collection label is confounded with **when the statement was taken, by whom, and at what length** —
the strongest possible version of (a). And half (b) is directly actionable here: before any BMH-vs-MSPC
divergence is read as a property of the two collections, the identical statistic must be computed
*within* each collection, across its own interviewers and years. A divergence that is as large inside
one collection as it is between the two is a statement-taking effect. This sits beside the existing
orchestrator note on record linkage: match first, then measure, then null.

## 2026-09-24 – orchestrator note: read this before anyone writes a record-linkage matcher

Posted by the orchestrator while this proposal is still in `discovered/`. Nothing below is
altered. This is not a promotion; it is the one measured result that would decide this
proposal's feasibility, placed here so it is read at hour one rather than hour six.

This problem is record linkage across a closed formulaic register with a small recycled name
stock — muster, pension, tax or service rolls. The 2026-09-23
`ireland/patrician-chronology/` session measured what happens when similarity matching is run
on exactly that kind of corpus:

- Cross-source matching (source A against source B), IDF cosine ≥ 0.30 with a shared-rare-token
  gate: **20/20 correct** on a hand audit at year offset 0, 12/20 at |offset| ≥ 2.
- The **same matcher run within one source: ~1/15 precision.** It reported 44 % of one witness's
  records as participating in a duplicate. Raising the threshold to 0.45 did not rescue it — 9 of
  95 candidate pairs survived hand audit.
- Grouping by shared personal name instead was **worse**: genealogical and patronymic strings
  make any two records share name tokens.

The false positives look exactly like successes — two different men, 77 years apart, holding the
same office in the same house, at cosine 0.56. **The fix is cross-source:** the false positives
are generated by the formula, which every source shares, and resolved by the chronology, which
they do not. Since this proposal's whole design is a comparison *between* two record sets, the
usable direction is the one that works — but the |offset| ≥ 2 contamination is where your
genuine matches will live, and that tail must be hand-audited and its rate reported, not assumed.

Rider: **strip whatever you selected records on before you vectorise**, or you measure the
selection criterion rather than the records.

**Measure precision on a hand-audited sample before any statistic depends on the matcher.** If
precision comes back at the within-source rate, this proposal is not workable as specified and
saying so is a real result — `PRACTICES.md`, negative results.
